# SQL-память агента: результаты эксперимента

**8 ноября 2026. Поиск отдельных механизмов, не leaderboard и не статистический accuracy benchmark.**

## Краткий результат

- **Найден воспроизводимый отдельный случай вреда ICL:** GLM переносит ошибочный SQL-grain из раннего задания в новые. В выбранном инциденте исходный запуск и два replay с прежней историей дают неверные знаменатели; исходный fresh и два fresh-повтора дают правильные знаменатели. Рост отказов занижается **с 15 до 9,12 п.п.**, а повторные попытки превращаются в вымышленный рост трафика.
- **Так же убедительной причинной демонстрации «память помогла дать верный ответ» не получили.** Есть правильные ICL против ошибочных fresh, но это ещё не доказывает роль истории.
- **Файловая память сама по себе почти не используется.** Luna/Haiku с исходной разрешающей инструкцией ничего не записывают; GLM сохраняет ответ и читает его лишь на T3. Более директивная, но общая инструкция вести заметки вызывает реальное чтение/перезапись у Luna — без гарантии правильности всех ответов.
- **Миграция не сломала основные ICL-ветки.** Агенты обнаруживают новый источник. Старый запрос Haiku сначала даёт пустой результат, затем исправляется.
- **Число действий и цена расходятся.** GLM ICL делает меньше действий, но стоит дороже fresh из-за контекста; у Haiku на той же задаче ICL, наоборот, дешевле.

### Важное ограничение архива

После окончания всех прогонов при подготовке HTML/финальной публикации контейнер был уничтожен инструментом. **Не всё удалось сохранить.** Из GitHub восстановлены полные оригинальные траектории **43/45 основных попыток + 2 диагностик**. Все 45 совпадают по SHA-256 с аудитом, выгруженным до сбоя. Сохранены также полный агрегированный аудит денег/токенов и все **448 shell-команд** 60 валидных попыток. Полные логи остальных 15 попыток и приватные native checkpoints утрачены.

Для пяти утраченных GLM-траекторий повторно исполнены **только инструменты**, без модельных API: 50 сохранённых команд на БД с исходными хешами; все exit codes совпали, механизм ошибочного denominator воспроизведён. Это **не восстановленные модельные диалоги**. Исходные финальные числа этих попыток в тексте опираются на анализ, сделанный до сбоя; оригинальный final response доступен не везде. Подробный перечень: [RECOVERY.md](RECOVERY.md), [recovery_inventory.json](public_results/recovery_inventory.json).

## 1. Устройство эксперимента

Использован новый синтетический стенд вместо публичных заданий CL-Bench. Генератор, seed и reference calculations заморожены до evaluation. Это снижает вероятность запоминания конкретных ответов, но не исключает знакомство с аналитическими шаблонами.

Модели: **`gpt-6-luna`** через ChatGPT/Codex Responses Lite; **`claude-haiku-5-5`** напрямую Anthropic; **`z-ai/glm-5.3-flash`** через OpenRouter. Доступы и GitHub write проверены реальными действиями до запуска.

| Режим | Между заданиями |
|---|---|
| Fresh / stateless | Новая сессия, никаких файлов/истории |
| ICL | Полная native история: вопросы, tool calls/results, ответы, возвращённое reasoning-состояние |
| Managed / optional | Новая сессия; только самостоятельно сохранённые файлы `../memory`, без auto-injection |

Единый инструмент — **bash**, обычные sqlite3/Python/cat/grep/sed; никаких bespoke memory/retrieval tools. Gold/оценки не возвращаются агентам. Все необходимые определения и факты восстановимы из **текущей** БД + README. Это тест **памяти-кеша**, не сохранения невосстановимых наблюдений.

Нет query-count reward, лимита 15 запросов или 50 строк. Tool output до **60 000 символов**, с явным truncation. Guards: 80 ходов / 15 минут на задачу, 60 s shell, 45 s CPU на процесс, 600 MiB адресного пространства. Задачи и DB hashes одинаковы во всех режимах, включая fresh после миграции.

### Пять заданий

| ID | Что проверяет |
|---|---|
| W1 | Операции против попыток, retries и terminal failures; temporal joins и routing aliases |
| W2 | Первый инцидент: уменьшенный deadline при стабильном upstream |
| T1 | Тренд/конфаундинг: pooled improvement, но кандидат хуже во всех 8 matched strata |
| T2 | Похожий симптом, другая причина: workers 16→4, queue 4→180, deadline неизменен |
| T3 | Необъявленная миграция attempt→operation grain и routing intent→actual execution cell |

До миграции: 20 таблиц, 32 500 операций, 40 480 попыток. После: 22 таблицы, добавлены 4 000 новых операций/outcomes. Чистые синтетические данные, маленький warehouse, явный бизнес-контракт. T1 задаёт требуемую стратификацию; это не тест самостоятельного открытия всех конфаундеров.

**45 основных попыток**, одна из них censored output. Ещё **15 диагностических**: один Haiku T1 с увеличенным output, четыре GLM T2 history/reset, две пятизадачные Luna-проверки инструкции памяти. Всего **59 завершённых + 1 censored** в исправленной изоляции. Старый технически невалидный пилот не включён.

## 2. Кейс «история навредила»: GLM

В первой W1 ICL-ветка ошибается примерно так:

```sql
SELECT COUNT(*) AS operations, SUM(natt) AS attempts
FROM operations o
JOIN attempt_events a ON a.operation_id = o.operation_id;
```

После join одна операция представлена несколькими строками: COUNT считает попытки, а SUM(natt) ещё раз размножает их число. Возникновение ошибки в **первой** задаче не вызвано межзадачной памятью. Проверяемый эффект истории — **перенос** её в W2, T1, T2.

В T1 стандартизованная разница получается **+1,75 вместо +3 п.п.**; направление эффекта всё же распознано. В T2:

| sync-south | Истина / fresh denominator | ICL с этой историей |
|---|---:|---:|
| Операций до → во время | 1000 → 1000 | 1150 → 1550 |
| Терминальных отказов | 25 → 175 | 25 → 175 |
| Доля отказов | 2,5% → 17,5% | 2,17% → 11,29% |
| Рост | **15 п.п.** | **9,12 п.п.** |

Дальше агент обсуждает якобы выросший объём трафика как альтернативное объяснение очереди. На деле выросло число повторных попыток, не бизнес-операций.

Два дополнительных history-запуска стартовали из точного **pre-T2 native checkpoint**; два fresh — без истории. БД и вопрос те же, никаких hints/gold/corrected SQL:

| Условие | Исходный | Replay 1 | Replay 2 |
|---|---|---|---|
| Прежняя история | Плохой denominator | Плохой denominator | Плохой denominator |
| Пустой контекст | Верный denominator | Верный denominator | Верный denominator |

**Не путать с 3/3 полностью правильных fresh-ответа:** исходный fresh имеет ошибки retries/queue timing. Оба дополнительных fresh-повтора имеют верные проверяемые числа. Это сильное свидетельство переноса конкретного ошибочного шаблона, но reset удаляет **всю** историю, а не единственную плохую строку. Кейc выбран после наблюдения; три реализации не дают population-оценки или статистической значимости.

Полные исходные логи: [main ICL T2](public_results/main-glm-icl/T2/trace.json), [history replay 1](public_results/diag-glm-t2-history-r1/T2/trace.json). Для остальных сохранены [команды](public_results/action_categories.json), [tool-only replays](public_results/recovery_tool_replays/) и [выписка шести результатов](public_results/glm_t2_observed_outcomes.json). Последняя явно помечена как восстановленная из предаварийных наблюдений, не оригинальный log.

## 3. Другие расхождения: не выдаём их за причинность

| Модель / исходный режим | T1 | T2 | T3 |
|---|---|---|---|
| Luna fresh | Числа верны | Неверная telemetry | Числа верны, дефект финального JSON |
| Luna ICL | Неверный workload mix; среда повлияла | Числа верны | Числа верны |
| Luna optional managed | Числа верны, слишком широкое SQL-окно | Числа верны | Числа верны, строка grain отличается |
| Haiku fresh | Output censored; отдельный repeat верен | Числа верны | Перепутаны reference/incident |
| Haiku ICL | Числа верны | Числа верны | Числа верны |
| Haiku optional managed | Числа верны | Числа верны после дорогого SQL | Числа верны |
| GLM fresh | Числа верны | Denominator верен; retries/timing ошибочны | Один процент противоречит counts |
| GLM ICL | Ошибочный grain / размер эффекта | Ошибочный grain / denominator | Числа верны |
| GLM optional managed | Числа верны | Числа верны | Числа верны, заметки прочитаны |

Таблица описывает численные результаты, **не полный pass по формату/SQL/интерпретации**. Fresh Haiku T2/T3 выполнены в separately named continuation после остановки T1. Диагностики не подменяют исходные клетки.

Примеры механизмов:

- Luna fresh T2 усреднила telemetry сразу за два часа и перенесла 10 workers / queue 92 в оба периода вместо 16→4 и 4→180. ICL считает раздельно. Возможная польза рабочего шаблона, но один контраст её не доказывает.
- Haiku fresh T3 назвала предикат **reference**-окна `is_incident`, затем развернула направление тренда. Это не неспособность обнаружить новую схему.
- GLM fresh T3 получила верные counts, но написала 3% вместо 10,5% в финале.
- Luna ICL T1 не смогла выполнить запрос сначала из-за отсутствующего `/dev/fd` в минимальном chroot, затем из-за синтаксиса SQL. Ошибка финального workload mix здесь **environment-affected**, не чистый эффект памяти.
- Luna managed W2 без каких-либо заметок спутала метрики и написала +65,5 вместо +18,5 п.п. Называть это вредом памяти нельзя: содержательной памяти не было.

## 4. Файловая память и устаревание

Исходная инструкция только сообщает, что persistent directory доступен. Luna/Haiku за пять задач ничего не записывают. GLM после W2 сохраняет `answer.json` (~9900 символов), не читает на T1/T2, но **читает на T3**. Затем пишет Markdown:

> Old memory (deadline change) was a different service (parcel-index) — do not reuse.

Это наблюдаемый пример правильного ограничения применимости нерелевантного опыта. Старый JSON **не удалён**: добавлена заметка. Без абляции не знаем, помогло ли чтение или только добавило расходы. [Полный T3 managed GLM](public_results/main-glm-managed/T3/trace.json).

### Отдельные проверки инструкции, не primary

- Даже явное объяснение fresh conversations / only memory persists не вызвало записи у Luna.
- Общая инструкция «в начале просматривай свои заметки, перед ответом поддерживай их» вызвала чтение и перезапись `notes.txt`. Содержание/структуру/удаление выбирает агент, не harness.
- Размеры после W1/W2/T1/T2/T3: **226 / 226 / 369 / 369 / 751 символ**. На T1 старые сведения заменены; на T3 прочитано устаревшее `active attempt_events`, затем схема перепроверена и файл заменён историческими интервалами v1/v2.

Это **не история сплошного успеха**: maintain-вариант T2 записал незавершённый Python-скрипт и выдал пустые массивы/assessment. Lifecycle-only T3 ошибочно отнёс reference-окно к старому feed и вывел нулевые placeholders. Причинной связи этих сбоев с записанными заметками не установлено. Сохранились точные команды и размеры памяти, не полные диалоги этих двух диагностических серий.

В основных ICL T3 все модели нашли новый источник. Haiku сначала получила пустой результат старого запроса, затем исправилась. Миграция **обнаружима** через registry и отсутствие старых данных для новых окон; это не самый сложный случай тихого изменения семантики при правдоподобном результате. Фонового dreaming здесь нет: актуализация происходит через свежие наблюдения при очередном задании.

## 5. Затраты

Сумма input — по всем ходам, с повторной передачей контекста; cached — подмножество. Shell invocation может содержать несколько SQL. Wall включает сеть/серверную вариабельность.

| T2 | Shell | Input | Cached input | USD | Wall |
|---|---:|---:|---:|---:|---:|
| Luna fresh | 7 | 24 707 | 0 | неизвестно | 70,5 с |
| Luna ICL | 4 | 87 423 | 23 680 | неизвестно | 56,9 с |
| Haiku fresh | 10 | 118 259 | 90 892 | $0,01271 | 66,8 с |
| Haiku ICL | 2 | 144 242 | 132 410 | $0,00646 | 27,3 с |
| GLM fresh | 8 | 45 048 | 39 168 | $0,00202 | 139,9 с |
| GLM ICL | 4 | 130 926 | 110 592 | $0,00683 | 23,6 с |

Для **Haiku** это пара совпадающих по проверяемым числам правильных ответов. У Luna/GLM ответы различаются; это не цена одинакового качества.

Fresh заново читает README/schema/справочники и конструирует SQL. Haiku ICL T2 сразу переходит к предметным запросам. Но цена чтения истории способна перевесить экономию действий: GLM ICL — в ~3,4 раза дороже fresh при половине shell-вызовов. У Haiku кэш и сокращение output делают ICL дешевле.

На T3 Luna с реально поддерживаемой памятью: **8 shell / 32 044 input / 0 cached**; ICL **4 / 109 585 / 53 504**, fresh **10 / 33 172 / 4 480**. Малый файл не устранил разведку, но не создал большого контекста. Это разные одиночные траектории и изменённая инструкция, не чистая оценка формата.

Не всю разницу input называем «лишней памятью»: меняются длины решений, часть истории полезна. В [аудите](analysis/cost_audit.md) раздельно prep W1/W2, target, first-target input, cache write/read, output, reasoning и эвристические категории действий. Смешанные команды не позволяют точно распределить модельные токены по «разведке»/«анализу».

### SQL >1 секунды

В покрытой CLI-части четыре invocation: **56,94 с** (Haiku managed T2, процесс завершён сигналом), исправленный запрос **3,05 с**, **47,31 с** (Haiku diagnostic T1, завершение с ошибкой), **5,90 с** (Luna lifecycle W1). Большинство остальных CLI-вызовов — доли секунды. Python sqlite3 не имеет полного отдельного таймера; для него сохранён wall всего shell. Поэтому это не исчерпывающий список всех SQL >1s.

### Общие расходы

- Anthropic ledger **$0,149116**, плюс **$0,000313** известных probes: **≈$0,14943**. Включён $0,005561 за обрезанный ответ. Оценка по зафиксированным тарифам, не invoice.
- OpenRouter ledger **$0,096286**, плюс **$0,000052** известных probes: **≈$0,09634**, источник usage.cost.
- Codex: **денежная стоимость неизвестна**, подписочный доступ, не $0.

Для некоторых ранних auth/catalog/error probes per-call usage нет; полного invoice из артефактов не восстановить. Бюджеты $20/$5 не приближены. Аудит до сбоя сверил 500 успешных turns без расхождений ledger/usage/цен и восстановил **48 803** Haiku thinking tokens, потерянных только в поле нормализованной аналитики.

## 6. Валидность и ограничения

1. Первая Luna-серия имела общий host `/tmp`; агент прочитал чужой скрипт. **Вся серия invalid**, сохранена отдельно. Исправлено полноценными отдельными chroot; все три Luna-ветки повторены. У исправленных 60 попыток DB hashes не менялись.
2. Исходный grader требует буквальных period labels, хотя schema лишь `string`. До сбоя выполнена отдельная нормализация однозначных алиасов без исправления чисел; strict grades сохранены. Полный файл этой поздней semantic-проверки утрачен. Низкие сырые fractions нельзя читать как accuracy. Числа таблицы выше проверялись с учётом этой проблемы.
3. Numeric pass не равен правильному SQL: слишком широкое окно может случайно совпасть на sparse snapshot; исполнимый evidence SQL может не подтверждать ответ; возможен невалидный хвост JSON.
4. Haiku fresh T1 упёрлась в output=8192; отдельный diagnostic с 32768 завершился с верными числами. Не считаем исходную остановку аналитическим провалом памяти.
5. Клиент сохранял/отправлял Anthropic thinking/signatures, GLM reasoning/details, Codex encrypted reasoning. Сохранённый аудит подтверждает prefix/reconstruction/payload checks, но не серверное использование состояния. Приватные checkpoints утрачены. Haiku использовала adaptive thinking с API-default effort; explicit medium не отправлялся. GLM/Luna medium.
6. Реальные cache misses сохранены, reasoning вручную не вырезалось. Параллельность и возможный provider-wide cache не дают cold-cache причинного сравнения времени/стоимости.
7. Одна маленькая синтетическая последовательность, постфактум выбранные diagnostics, без независимой test выборки. Нет долгосрочного накопления огромного объёма памяти. Нельзя выводить средний эффект памяти, superiority моделей или решение проблемы устаревания вообще.

**Следующая содержательная проверка, пока не выполненная:** старый SQL, который успешно исполняется и даёт правдоподобный, но уже неверный результат; много похожих старых инцидентов; абляция конкретного шаблона с sham-контролем; фоновые периоды в БД, чтобы неправильный фильтр времени не проходил случайно.
